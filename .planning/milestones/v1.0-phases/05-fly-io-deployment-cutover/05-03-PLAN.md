<task type="auto">
  <name>Task 2: Confirm SQLite volume persists across restart</name>
  <files></files>
  <action>
Run a no-op redeploy and confirm the SQLite file survives container restart:

```bash
# No-op redeploy (same image, same config — purely tests volume persistence)
cd /Users/sn0w/Documents/dev/lifeboard-mono/server && fly deploy

# After deploy completes, check the volume
fly ssh console -C "ls -la /data/" --app mega-planner-api
```

Expected: `/data/lifeboard.db` is still present with the same non-zero size as after Plan 02.

WHY this confirms persistence: A Fly.io persistent volume survives machine stop/start and redeploy
cycles. If the SQLite file were stored on ephemeral machine storage, it would vanish on redeploy.
Seeing the same file with the same size after redeploy confirms the volume is correctly mounted.

If the file is gone or zero bytes after redeploy: the volume is not mounted. Check fly.toml [mounts]
section (Plan 01 task) and re-run Plan 02.
  </action>

<task type="checkpoint:human-action">
  <name>Task 3: Decommission PostgreSQL after 48-hour rollback window</name>
  <files></files>
  <action>
Wait 48 hours after the smoke test passes (Task 1). If no production issues surfaced during that
window, run the decommission sequence. This step is time-delayed — do not run immediately after
Task 2. Resume this plan after 48 hours have elapsed.

```bash
# Step 1: Detach the PostgreSQL cluster from the app
# (DATABASE_URL secret is already unset from Plan 02 — detach is clean)
fly postgres detach mega-planner-api-db --app mega-planner-api

# Step 2: Destroy the PostgreSQL cluster (IRREVERSIBLE — only run after rollback window)
fly apps destroy mega-planner-api-db

# Step 3: Confirm cluster is gone
fly machine list --app mega-planner-api-db 2>&1
```

WHY `fly apps destroy` not `fly mpg destroy`: The cluster is unmanaged Fly Postgres (an ordinary
Fly app running Postgres), not Fly Managed Postgres. `fly apps destroy` is the correct command.

ROLLBACK OPTION (if issues found within 48h): The PostgreSQL cluster is still running. Revert
the DATABASE_PATH secret and restore DATABASE_URL to roll back. The local SQLite file
(server/mega_planner_dev.db) is the migration export — new production writes since cutover will
not be in it (data divergence), so rollback must be treated as a data loss event. Only roll back
for catastrophic issues.
  </action>
  <verify>
    <automated>fly machine list --app mega-planner-api-db 2>&1</automated>
  </verify>
  <done>fly machine list --app mega-planner-api-db shows no machines or app-not-found error, confirming PostgreSQL cluster is destroyed</done>
